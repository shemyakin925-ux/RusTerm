# Критическая рецензия RusEquity Terminal

## 1. ПРОБЛЕМЫ (по убыванию критичности)

**1. Один человек + LLM-агенты не вытянут этот объём.** В ТЗ ~80% трудоёмкости — не код, а работа с данными: парсинг e-disclosure, ручная разметка governance, верификация корпоративных действий, сопоставление МСФО/РСБУ, поддержка 30–150 эмитентов × десятки событий каждый × годы истории. Это годы работы даже для команды из 3–5 аналитиков. Бюджет внимания LLM-агентов конечен и расходуется на каждый тикет; качество падает экспоненциально от сложности.

**2. Нет определения MVP-скоупа.** Фазы 0–6 — это roadmap продукта на годы, не ТЗ на pre-MVP. До какой конкретной фазы проект дойдёт «в первом релизе»? Без cut-line «всё остальное — потом» это не спецификация, а wishlist. Pre-MVP должен быть описан одной фразой: «показываем по 10 бумагам цену, TR, 3 мультипликатора, 1 governance-факт — сходится с ручным расчётом».

**3. Flutter для desktop с таблицами на тысячи строк — красный флаг уже сейчас, а не «в ADR потом».** ТЗ само это признаёт («Flutter слаб»), но оставляет решение на потом. Это значит, что либо придётся переписывать desktop-слой (потеря 2–4 месяцев), либо терминал на десктопе будет непригоден для целевого сценария (аналитик за столом, 30–150 бумаг, фильтрация, сортировка, multi-screen). Сценарий «частный инвестор с 30–150 бумагами» — это desktop-сессии, не мобильные.

**4. Corporate actions — неразрешимая задача в предложенном виде.** «Сплиты, допэмиссии, байбэки, смена тикера, редомициляция, конвертация расписок» — это не «слой», это отдельный многолетний проект с ручной верификацией по каждому эмитенту. Газпром, Яндекс, X5, TCS — у каждого уникальная история, дыры в раскрытии 2022–2024, неточные коэффициенты. ISS даёт коэффициенты не для всех событий, e-disclosure не машиночитаем, IR-сайты ломают ретроспективу. Без ручного труда по каждой бумаге скорректированные ряды будут врать, и все downstream-расчёты (TR, перцентили, факторы) поедут вместе с ними.

**5. Governance Score — самый ценный и самый нереализуемый блок.** Прекрасно описан концептуально, но:
   - 20 эмитентов ручной разметки — это 200–400 часов работы вдумчивого аналитика, не LLM-агента. Кто её сделает?
   - Реестр обещаний требует мониторинга всех публичных выступлений, звонков, презентаций 5–10 лет назад по 100+ эмитентам. Это невозможно собрать задним числом даже с LLM.
   - «Тихая отмена» через сравнение версий IR-материалов — половина сайтов не имеет архива, у второй половины версии не размечены, третья удалила старые презентации.
   - LLM-извлечение из e-disclosure с антиботом и хрупкой вёрсткой — основной источник будет терять 20–40% событий, а governance без полноты = мусор.

**6. Нет операционной модели.** Кто мониторит сломанные парсеры? Кто реагирует, когда ISS сменит формат? Кто проверяет suspect-данные? Кто обновляет golden-files при смене методологии? Где SLA на обновления? «LLM-агенты» — это не команда, это инструмент. Процесс эксплуатации не описан ни в одном разделе.

**7. Отсутствует threat model по данным.** Что если ISS закроет бесплатный доступ, ограничит запросы, изменит TOS? Что если e-disclosure поменяет вёрстку? Что если ЦБ прекратит публикацию КБД? Что если Росстат пересмотрит ИПЦ задним числом? В ТЗ ни одного fallback-сценария. Для долгоживущего терминала это смертельно.

## 2. ЧТО ДОБАВИТЬ

**В архитектуру и план:**
- **Single source of truth на тикер** — не «internal instrument_id», а полный mapping: SECID ↔ ISIN ↔ ticker history ↔ board ↔ тип (акция/преф/ГДР) с датами действия. Без этого любая агрегация будет ломаться на редомициляциях.
- **Версионирование методологии** — не только `method_version` для governance, но и для формул TR, ROIC, перцентилей, факторов. Всё, что влияет на скор, версионируется. Иначе через год вы не воспроизведете собственные цифры.
- **Data lineage** — для каждого числа в UI: откуда взято (источник + URL + дата выгрузки + версия парсера + raw). Без этого нельзя ни аудировать, ни чинить.
- **Observability** — метрики ingestion (success rate, лаг, число suspect-записей), метрики API, метрики LLM-извлечения (confidence, ручные vs автоматические). Без этого проект невозможно эксплуатировать.

**В продукт:**
- **Определение MVP-скоупа** — 10–20 бумаг вручную верифицированных, без governance, без факторов, с ручным обновлением данных. Цель MVP: доказать, что pipeline работает end-to-end на малом объёме.
- **UX-сценарии** — не «лучший snapshot», а конкретные сценарии: «я хочу понять, почему Yandex упал сегодня», «сравнить Татнефть-ао и Татнефть-ап по дивидендной политике», «найти бумаги с наибольшим кэшем на балансе в нефтегазе». Без сценариев — это набор таблиц.
- **Требования к перформансу с цифрами** — не «<2 с», а «p95 <1.5 с на cold cache, <300 мс на warm, размер снапшота не более X МБ».
- **Offline-режим** — для мобильного сценария обязателен. Не описан.
- **Экспорт данных** — CSV/Excel/Parquet для дальнейшего анализа. Целевой пользователь работает с 30–150 бумагами — ему нужны свои модели.

**В governance:**
- **Чёткий список источников событий по приоритету** — что первичное, что fallback. Сейчас e-disclosure + IR-сайт = два несовместимых канала с разной полнотой. Какой побеждает при конфликте?
- **Процедура dispute resolution** — если LLM извлекла событие неверно, как пользователь/оператор это исправляет? Где хранится ground truth?
- **Этические guardrails** — governance-скор = публичная оценка отношения к миноритариям. Кто несёт ответственность за ошибку в скоре? Что если мажоритарий подаст в суд за «порочащие деловую репутацию сведения»? Disclaimer «это не рейтинг» не снимает риск.

**В правовое:**
- **GDPR/152-ФЗ compliance** — если приложение собирает что-то о пользователях. Не описано.
- **Cookie/analytics policy** — для будущей публичной раздачи.
- **Политика хранения** — что с данными удалённых пользователей.

## 3. НЕРЕАЛИЗУЕМО или сильно недооценено

**1. «Ручная разметка 20 эмитентов для валидации governance» — 200–400 человеко-часов.** Это не задача LLM-агента, это работа одного человека с deep domain expertise, читающего 20 годовых отчётов + сотни раскрытий + презентации за 5–10 лет по каждому. В одиночку — 3–6 месяцев full-time. После этого нужно поддерживать разметку: новые эмитенты, новые события, drift.

**2. «Реестр обещаний» с 5–10-летней историей по 100+ эмитентам.** Невозможно собрать ретроспективно. У 80% эмитентов нет машиночитаемой истории презентаций, звонки не расшифровывались, дивполитика менялась без фиксации старых версий. Реалистичный скоуп — только с момента запуска проекта, форвард-only. Но тогда бэктест governance невозможен, и валидация по известным кейсам (Газпром 2022) требует отдельной ручной работы.

**3. Парсинг e-disclosure в проде.** Это не «хрупкая зона» — это сизифов труд. Антибот, смена вёрстки, CAPTCHA, разные форматы раскрытий (PDF, DOC, HTML), необходимость OCR для сканированных документов. 30–50% времени разработчика уйдёт на поддержку парсеров, а не на продукт. И всё равно покрытие будет неполным.

**4. Pre/post-2022 перцентили + факторы + бэктест — годы работы.** Бэктест требует десятилетия чистых PIT-данных. У вас их нет. Survivorship bias учтён в ТЗ, но не учтён look-ahead bias в МСФО-пересчётах, изменения в учётной политике, M&A-корректировки, инфляционные пересчёты (IAS 29 для РФ с 2022). Без корректной PIT-инфраструктуры бэктест «фактора» будет доказывать не то, что вы думаете.

**5. LLM на MacBook Pro M5 single-thread для production-pipeline.** Даже с low-priority, обрабатывая тысячи событий governance + сотни summary + объяснения аномалий — это не справится. Либо локальная модель будет настолько слабой, что качество извлечения упадёт ниже порога, либо время отклика убьёт UX.

**6. «Лучший research-snapshot» как заявленная цель.** Такой снапшот у вас уже есть: это сайт эмитента + Smart-Lab + Investing + Telegram-каналы аналитиков + пара отчётов. Чтобы быть «лучше», нужна уникальная добавленная стоимость. В ТЗ она размазана по governance и перцентилям, но не сформулирована в одну фразу, ради которой пользователь будет пользоваться именно этим терминалом.

## 4. ЧТО РЕАЛИЗУЕМО В ПЕРВУЮ ОЧЕРЕДЬ

**1. MVP за 2–4 месяца:**
   - 15–20 эмитентов вручную отобранных, с верифицированными corporate actions
   - ISS-клиент с троттлингом, дисковый кэш, postgreSQL схема
   - Цена + adjusted price + дивиденды с e-disclosure (ручной ввод за 1 день)
   - Total Return до налога, бенчмарк MCFTR
   - 3–4 базовых мультипликатора (P/E, EV/EBITDA, P/B, ROE) из МСФО ручным вводом
   - Простой web-UI на FastAPI + Jinja, не Flutter
   - **Никакого governance, никаких факторов, никакого мобильного UI**

**2. После MVP — горизонтальное расширение покрытия эмитентов:**
   - Парсеры e-disclosure (начиная с топ-30 по капитализации)
   - Автоматическое извлечение дивидендов и корпоративных действий
   - Валидация на ручном baseline

**3. Governance — как отдельный модуль с форвард-only данными, начиная с 10 эмитентов вручную.** Без бэктеста, без ретроспективного реестра обещаний. Только текущий скор + история с момента запуска.

**4. Desktop-решение — до начала фронтенд-разработки, не после прототипа таблицы.** Либо Tauri+React+TanStack сразу, либо честно: «MVP только на web, desktop — это фаза N, не раньше».

**5. Выбросить Flutter из MVP.** На мобильном можно запустить web-приложение через PWA или Capacitor. Это даст 80% мобильного опыта за 10% усилий.

## 5. САМОЕ ОПАСНОЕ МЕСТО

**Сочетание: один разработчик + LLM-агенты + обязательство поддерживать ручную верификацию governance для 20+ эмитентов + парсинг нестабильных источников + поддержка desktop-таблиц в Flutter + бэктест + правовая чистота при будущей публикации.**

Это 8–15 человеко-лет работы, описанных как проект одного человека. **ТЗ описывает команду из 5–8 человек, маскируя это под «LLM-агенты».** LLM ускоряет отдельные такты (написать код, извлечь сущности из текста), но не заменяет: чтение 20 годовых отчётов вручную, принятие решений по методологии, разбор конфликтов в данных, поддержку сломанных парсеров по ночам, обновление разметки при смене законодательства. У одного человека есть ~2000 продуктивных часов в год, из них 30–50% уйдёт на операционку, а не на разработку. За 12 месяцев реально сделать MVP из п.4 выше. Всё остальное из ТЗ — это работа на 3–5 лет, в одиночку не вытянуть, и проект умрёт от усталости и расползания скоупа задолго до governance-скора.

**Главная рекомендация: сократить ТЗ в 5–7 раз, начать с MVP из 15 бумаг без governance и факторов, и только после стабильной эксплуатации 6+ месяцев решать, стоит ли вообще лезть в governance-модуль.** Скорее всего, governance-скор — это отдельный коммерческий проект с собственной командой аналитиков, и встраивать его в личный терминал одного человека — гарантированный провал обоих начинаний.
