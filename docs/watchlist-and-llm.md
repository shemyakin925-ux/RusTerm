# Watchlist и массовые LLM-операции

Детали к README §5 и §6. Приведено в соответствие с ADR-0003 (SQLite —
единственная система записи), ADR-0005 (адресация по `instrument_id`)
и ADR-0002 (peer set).

---

## 1. Watchlist

### 1.1 Где хранится

**Система записи — SQLite.** Файлы JSON остаются только форматом обмена
(экспорт, импорт) и форматом журнала аудита. Причины — в ADR-0003:
атомарность массовых операций на файлах не обеспечивается, откат к версии
на дату — запрос, а не копирование файла, и при 500 бумагах экран списка
не должен читать 500 отдельных файлов покрытия.

```
watchlist            id, name, description, update_schedule, created_at
watchlist_version    id, watchlist_id, version, created_at, action, actor
watchlist_member     watchlist_version_id, instrument_id, note, added_at
watchlist_group      id, watchlist_id, name, created_at
watchlist_group_member  group_id, instrument_id, added_at, removed_at
watchlist_filter     id, watchlist_id, name, criteria_json, updated_at
```

Версия неизменяема: изменение состава создаёт новую строку
`watchlist_version` и новый набор `watchlist_member`. Текущее состояние —
максимальная версия. Откат — вставка новой версии, копирующей состав
указанной; история не переписывается никогда.

**Группы и фильтры принадлежат списку, а не версии.** Если привязать их
к `watchlist_version_id`, то переименование группы или добавление в неё одной
бумаги породит новую версию всего списка из 500 позиций — а группы по README §5
пересекаются и живут своей жизнью, независимо от состава списка. Поэтому состав
группы версионируется отдельно, интервально: `removed_at IS NULL` даёт текущий
состав, а состав на любую прошлую дату восстанавливается по `added_at` /
`removed_at`. Неизменяемость истории соблюдается и здесь — строки не удаляются,
у них проставляется `removed_at`.

Инструмент может состоять в нескольких группах одновременно и может состоять
в группе, не входя в текущую версию списка (например, выбыл из watchlist,
но остаётся в группе «наблюдение»). Экран группы показывает такие позиции
отдельной пометкой, а не молча их прячет.

### 1.2 Состав

Элемент списка ссылается на `instrument_id`, не на тикер (ADR-0005).
Тикер, ISIN и биржа берутся из справочника при отображении, поэтому смена
тикера не рвёт список и показывается как событие.

Динамические фильтры хранятся как критерий, а не как результат:

```json
{
  "name": "All tankers cap>500M",
  "markets": ["US", "UK", "CA"],
  "industry": "Maritime/Tanker",
  "market_cap": {"min": 500000000, "max": 5000000000},
  "exclude": ["delisted", "in_distress"]
}
```

Результат применения фильтра фиксируется в версии списка при каждом
пересчёте — иначе состав меняется молча, ровно как peer set в ADR-0002.

### 1.3 Покрытие

`coverage` — строка в БД на пару (instrument, блок снапшота):

| Поле | Смысл |
|---|---|
| `block` | `prices`, `fundamentals`, `ownership`, `corporate_actions`, `governance`, `industry_metrics`, `peer_set`, `llm_summary` |
| `status` | `ready` / `stale` / `processing` / `missing` / `error` |
| `last_update` | когда блок последний раз собран |
| `reason` | причина для `missing` и `error`: отчёт не опубликован, peer set не подтверждён, провайдер вернул ошибку, требуется ручная верификация |

Пробел показывается, а не замалчивается — жёсткое требование. Рядом с
покрытием данных выводится `peer_set_coverage` (ADR-0002).

### 1.4 Импорт и экспорт

Экспорт — CSV или JSON, адресация тикерная, для человека:

```csv
ticker,market,isin,industry,note,added_at
AAPL,US,US0378331005,BigTech,"Кэш + buyback",2026-09-01
```

Импорт — через `resolve_ticker(ticker, market, as_of)`. Строка, которая
не разрешилась или разрешилась неоднозначно, попадает в отчёт импорта
и **не добавляется молча**. Импорт из портфельных трекеров — не в MVP.

## 2. LLM: пополнение базы

### 2.1 Конвейер

```
Сообщение → классификация намерения → read-only инструменты
          → dry-run → подтверждение пользователя → выполнение → аудит
```

Ни один шаг до подтверждения не меняет состояние.

### 2.2 Намерения

| Интент | Что делает |
|---|---|
| `add_instruments` | добавить конкретные бумаги |
| `add_industry` | добавить отрасль с фильтром |
| `add_index` | добавить состав индекса или холдинги ETF |
| `add_peers` | добавить пиров существующей компании |
| `update_summaries` | обновить LLM-summary по списку |
| `compare` | сравнить 2-5 компаний |
| `ask_company` | вопрос по снапшоту |
| `ask_industry` | вопрос по отрасли |

### 2.3 Предохранитель — детерминированный

Самооценка модели (`confidence`) **из ветвления убрана**: это неоткалиброванное
число, полученное от той же модели, чьё решение оно должно проверять.
Логировать можно, принимать по нему решения — нет.

Операция уходит на выполнение, только если **все** условия выполнены:

1. Намерение распознано одним из списка выше.
2. Все обязательные параметры намерения заполнены.
3. Каждый инструмент разрешён через `resolve_ticker` до `instrument_id`
   однозначно.
4. Размер результата не превышает лимит операции (по умолчанию 100).
5. Пользователь подтвердил показанный список.

Не выполнено любое — уточняющий вопрос, а не действие наугад.

### 2.4 Инструменты

Все read-only:

- `resolve_ticker(ticker, market, as_of) → instrument_id | ambiguous | not_found`
- `list_industry_instruments(industry, filters) → [instrument_id]`
- `get_peer_set(instrument_id) → peer_set с версией и origin`
- `get_snapshot_block(instrument_id, block) → Measure[]`

Инструмент, меняющий состояние, LLM не даётся ни одного. Изменения вносит
приложение после подтверждения.

### 2.5 Dry-run

Показывается полный список с пометкой по каждой позиции: будет добавлена,
исключена фильтром, уже в списке, не разрешилась. Прогноз времени сбора
**не показывается**, пока не измерен на реальных источниках, — в прежней
редакции документа стояли две оценки, расходившиеся на порядок, обе взятые
без замера.

### 2.6 LLM-summary

Вход: текущий снапшот, предыдущий снапшот для diff, последние раскрытия
из манифеста, peer set с мультипликаторами.
Выход: `summary` (3-5 предложений), `highlights`, `risks`, `citations`.

Числа в тексте берутся из снапшота подстановкой, не сочиняются моделью.
Утверждение с числом без ссылки в `citations` — баг, проверяемый тестом.

Хранение — таблица `llm_summary`: `instrument_id`, `created_at`, `model`,
`prompt_hash`, `snapshot_version`, текст, `citations`.

## 3. Безопасность массовых операций

1. **Dry-run по умолчанию.** Без подтверждения ничего не меняется.
2. **Атомарность.** Операция применяется целиком либо не применяется —
   одна транзакция SQLite, одна новая версия списка.
3. **Откат** любой операции к предыдущей версии.
4. **Лимит** — по умолчанию 100 инструментов; больше — отдельное
   подтверждение. Лимит относится к **правке состава** списка: добавить
   сектор, удалить группу, импортировать файл. Он защищает от разовой
   ошибочной массовой правки.

   **Плановый обход по расписанию под лимит не подпадает и подтверждения
   не требует.** Это не правка состава, а сбор данных по уже утверждённому
   составу: версия списка не создаётся, `watchlist_member` не меняется,
   меняются только снапшоты и `coverage`. Поэтому обновление 500 бумаг из
   критерия готовности MVP (README §15) идёт без ручных действий, а
   разбиение обхода на пачки — деталь планировщика, а не операция над
   списком. Сбой на бумаге не останавливает обход: её `coverage` остаётся
   в прежнем состоянии с причиной, остальные обновляются.
5. **Аудит** — `audit_log` в БД плюс дублирование в `logs/audit.jsonl`
   только на добавление: время, действие, список, подтверждение, результат.
6. **Неопределённость — вопрос,** а не действие: см. 2.3.
