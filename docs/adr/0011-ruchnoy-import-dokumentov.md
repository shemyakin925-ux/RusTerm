# ADR-0011. Ручной импорт документов: файл, модель по API, детерминированный контроль

**Статус:** принято (решение пользователя, дополнение от 10.09.2026).

## Контекст

Правило ADR-0010 §3 честно отвечает «этот эмитент машинно недоступен»,
но на этом обрывается: пользователю некуда деть годовой отчёт, который
у него есть в виде файла. Нужен второй вход в данные — не сеть, а диск.

Пользователь сформулировал три ограничения:

1. импортируются **годовые и иные отчёты и прочие документы** компаний;
2. форматы **разные, не только PDF**;
3. вариант работы с моделью **ровно один — по API**; локальной модели
   в проекте нет.

Прототип у пользователя уже работает вне репозитория:
`~/TextConv/rusconv` (PDF → постраничный текст → локальная gpt-oss-20b →
детерминированный валидатор → CSV/JSON). Его практический вывод, взятый
как данность: **модель ошибается на широких таблицах — путает колонку,
из которой взяла число.** Валидатор ловит выдуманные числа и
подправленные цитаты, но семантику колонки гарантировать не может.
Значит, доверие к извлечённому факту — не бинарное «есть/нет», а
измеряемое свойство, которое обязано доехать до снапшота.

## Решение

**Импорт — конвейер из трёх ступеней с разной природой доверия, и
граница между ними видна в данных.**

```
файл  ──①──>  текст по страницам  ──②──>  записи-кандидаты  ──③──>  факты
     детерм.                     модель по API           детерм. контроль
```

### ① Извлечение текста — детерминированное, без модели

Модуль `rusterm/manual/extract.py`. Один вход: путь к файлу. Один
выход: страницы (`page_no`, `text`) плюс `sha256` исходника.

Форматы и правило выбора: по содержимому файла, не по расширению.
`.txt`/`.md`/`.csv`/`.tsv`/`.json`/`.htm`/`.html` — стандартной
библиотекой; `.pdf`, `.docx`, `.xlsx` — библиотекой, если она есть,
иначе **значение-ошибка `format_unsupported` с именем недостающего
пакета**, а не исключение и не молчание. Формат без текстового слоя
(скан) — `no_text_layer`; OCR в проекте нет и не планируется.

Ступень тестируется целиком без модели и без сети.

### ② Извлечение записей — модель, ровно по API

Клиент живёт в `rusterm/providers/llm_api.py`, потому что HTTP
разрешён только в провайдерах (проверка 8 приёмки). Он
OpenAI-совместимый: база и имя модели — из окружения
(`RUSTERM_LLM_BASE_URL`, `RUSTERM_LLM_MODEL`), ключ — из
`RUSTERM_LLM_API_KEY` и **только оттуда**.

- Ключа нет → `ConfigError` значением, ступень ② не выполняется,
  импорт останавливается на ① с внятным текстом. Никаких «зашитых»
  ключей, никаких ключей в git, никаких ключей в отчётах и логах.
- Локальный сервер модели (LM Studio, Ollama) — **не поддерживается**:
  пользователь оставил одну опцию, и вторая калитка удваивает
  поверхность ошибок.
- Тесты не ходят к модели: подставной клиент возвращает записанные
  ответы. Ни один тест не требует ключа.

Каждая запись-кандидат обязана нести: компанию, метрику, значение,
единицу с масштабом, период, **дословную цитату и номер страницы**.
Запись без цитаты отбрасывается на ступени ③ целиком.

Категории записей наследуются у прототипа, потому что они оправдались:
`financial` — отчётность; `physical` — натуральные операционные метрики
(тонны, суда, мощности); `other` — корпоративные события с числами.

### ③ Контроль — детерминированный, без модели

`rusterm/manual/verify.py`, чистые функции. Две проверки, обе
механические:

1. цитата **дословно** присутствует на своей странице;
2. числа из значения **содержатся** в цитате.

Исход — `verified: yes|no`, и он честен о своих пределах: проверка не
доказывает, что модель взяла число из правильной колонки правильного
периода. Поэтому:

- запись с `verified=no` **сохраняется**, но помечается;
- **факт из ручного импорта с `verified=no` не участвует в мерах
  снапшота** — он виден в карточке источника и в экспорте, но не
  попадает в числитель ни одной формулы. Причина покрытия —
  `manual_unverified`.

### Происхождение: ручной факт отличим от машинного навсегда

Факт получает `source_kind` из перечисления: `provider` (сеть) или
`manual` (импорт). Локатор ручного факта — не URL, а
`sha256:<хэш файла>#page=<N>`; lineage несёт имя модели, версию
промпта и исход контроля.

Это **инвариант, а не соглашение**: смешать ручной и машинный факт
в одном значении нельзя, и снапшот обязан уметь показать, что число
пришло из файла пользователя, а не из регулятора.

### Что импорт не делает

Не ходит в сеть за самим документом (файл даёт пользователь), не
перезаписывает машинные факты, не создаёт эмитента без явного
указания, не выполняет OCR, не работает с локальной моделью.

## Следствия

- Появляется таблица `document` (хэш, имя, формат, страницы, эмитент,
  дата импорта) и связь факта с документом. Схема — одна миграция.
- `~/TextConv/rusconv` остаётся отдельным инструментом пользователя;
  в репозиторий он не переносится. Из него берутся **решения**
  (три категории, дословная цитата, детерминированный валидатор,
  честность о колонках), а не код.
- Ручной импорт закрывает исход `manual_import_required` из ADR-0010
  §3: программа не просто отказывает, а называет работающий путь.
