# ADR-0012. Параллельное исполнение: ветка на полосу, зона файлов, схема первой

**Статус:** принято (координатор, 10.09.2026, по вводной пользователя
«ZCode позволяет делать до 50 параллельных процессов»).

## Контекст

До сих пор исполнитель был один и работал в одной ветке
последовательно: пункт — коммит — приёмка. Правило «одна ветка, один
процесс» дало предсказуемую рецензию: `git log` читается сверху вниз,
каждый коммит зелёный, приёмка одна.

Исполнитель может вести до 50 процессов сразу. Наивный перенос старого
порядка на 50 процессов ломает ровно то, ради чего порядок заведён:

- **миграции.** Каждая новая миграция требует уникального номера и
  подъёма `_SCHEMA_VERSION`. Две полосы, тронувшие `rusterm/store/db.py`
  одновременно, дают либо конфликт слияния, либо — хуже — две миграции
  с одним номером и разошедшуюся схему у пользователя;
- **приёмка.** `bash agent/acceptance.sh` — свойство ветки целиком.
  Полсотни процессов в одной ветке делают её результат бессмысленным:
  непонятно, чья правка покрасила прогон;
- **рецензия.** Отчёт «сделано» проверяется прогоном. Если границы
  работы не видны в git, проверить нечего.

## Решение

**Ветка на полосу, зона файлов на полосу, схема — до разветвления.**

### 1. Три фазы, а не одна

```
Фаза 0  ФУНДАМЕНТ   один процесс, одна ветка. Схема, реестры,
        (посл.)     интерфейсы, причины. Заканчивается тегом-головой.
                          │
        ┌─────────────────┼─────────────────┐
Фаза 1  │ полоса L1 │ полоса L2 │ … │ полоса Ln │   параллельно,
        │ ветка     │ ветка     │   │ ветка     │   от головы фазы 0
        └─────────────────┼─────────────────┘
                          │
Фаза 2  ИНТЕГРАЦИЯ   один процесс: слияние, сквозные тесты, приёмка.
        (посл.)
```

Фаза 1 не начинается, пока фаза 0 не дала зелёную приёмку. Это не
осторожность, а арифметика: миграции сериализуемы по определению.

### 2. Зона файлов — часть задания, а не договорённость

У каждой полосы в ТЗ выписан **список путей, которые она правит**, и
он не пересекается с чужими. Полоса, которой понадобился чужой файл,
**останавливается и пишет об этом в отчёт** — она не правит его «на
минутку». Общие файлы разрешает фаза 2.

Три файла принадлежат фазе 0 навсегда и не правятся ни одной полосой:
`rusterm/store/db.py` (миграции), `rusterm/markets.py` (реестр рынков),
`rusterm/reasons.py` (перечень причин). Полосе, которой нужна новая
причина или строка рынка, фаза 0 её уже добавила — заранее, по ТЗ.

### 3. Ветка полосы

`agent/n<ночь>-<ID полосы>`, отведена от головы фазы 0, в неё же и
коммитит. В чужую ветку не коммитит никто. Каждая полоса заканчивает
**зелёной приёмкой на своей ветке** — 13 из 13, без исключений и без
«зато у других зелено».

### 4. Слияние — работа координатора, а не исполнителя

Полоса не сливает себя в общую ветку. Она пушит свою ветку и пишет в
отчёт строку «готова к слиянию: <ветка>, <sha>, приёмка 13/13».
Сливает координатор: тогда конфликт виден человеку, а не разрешается
ночью в одиночку.

### 5. Сколько полос осмысленно

Не 50. Полоса требует непересекающейся зоны файлов, своего записанного
payload и своей приёмки — этого хватает примерно на десяток полос за
ночь. Дальше процессы начинают делить файлы, и выигрыш съедается
конфликтами.

Внутри полосы параллелизм не ограничен: разведка источника, выкачка
и обрезка payload, прогон подмножества тестов идут сколь угодно широко —
там нет общего состояния.

## Следствия

- Приёмка остаётся ground truth, но теперь у неё есть адрес: ветка.
- `agent/STATE.json` перестаёт быть одним файлом на исполнителя:
  каждая полоса ведёт `agent/state/<ID>.json`, иначе процессы затирают
  друг друга. Фаза 2 сводит их в общий `STATE.json`.
- Отчёт тоже на полосу: `agent/REPORT-<N>-<ID>.md`, append-only по
  прежним правилам R1–R4. Общего файла отчёта у параллельной ночи нет.
- Правило «один пункт — один коммит» не меняется; меняется только то,
  в какую ветку он ложится.
