# ADR-0003. Локальное приложение и выбор хранилища

**Статус:** принято (06.09.2026)

## Контекст

Приложение ставится на компьютер пользователя, работает без учётной записи
и серверной части, у каждого пользователя свой набор данных. Обмена между
установками нет, кроме явного экспорта списков.

README §11 в первой редакции называл PostgreSQL хранилищем метаданных. Это
решение принималось по инерции от серверной архитектуры и с моделью
развёртывания не согласуется: оно требует от пользователя установить
и обслуживать СУБД ради приложения, которое должно запускаться двойным щелчком.

## Оценка объёма

Верхняя граница MVP — **500 бумаг**:

| Данные | Оценка строк |
|---|---|
| Факты отчётности | 500 × 60 концептов × 40 периодов ≈ 1,2 млн |
| Производные величины с `method_version` | ≈ 1,2 млн |
| Котировки (дневные, 10 лет) | 500 × 2 500 ≈ 1,25 млн |
| Ownership, корпдействия, события | ≈ 300 тыс. |
| **Итого** | **порядка 4 млн строк, единицы гигабайт** |

Для SQLite это по-прежнему незначительный объём: на таких таблицах с
правильными индексами запросы идут за десятки миллисекунд. Сырые файлы
в БД не попадают — они лежат в content-addressed store на диске.

**Узкое место при 500 бумагах — не база, а сбор.** SEC EDGAR разрешает
10 запросов в секунду; полное обновление 500 эмитентов по всем блокам —
это десятки тысяч запросов, то есть часы. Отсюда требование к планировщику:
инкрементальный сбор по индексу изменений, а не полный обход. Проектируется
на Этапе 3.

## Retention сырья

При 500 эмитентах за 10 лет сырьё — единственная статья, способная вырасти
до десятков гигабайт (один XBRL companyfacts — 5-20 МБ).

1. **Всегда хранится** то, из чего извлечены факты: XBRL, JSON API-ответов,
   таблицы. Это база lineage (ADR-0001), выбрасывать нельзя.
2. **Полные PDF и HTML** хранятся по настройке `raw_retention`:
   `full` — всё, `facts_only` — только документы, давшие хотя бы один факт.
   URL и sha256 остаются в манифесте в любом случае, документ до-качивается
   по требованию.

   **Из-под `facts_only` выведены документы, которые парсер не разобрал**
   (ветка E4 в `processes.md`) и всё, что стоит в очереди верификации.
   Ноль фактов у такого документа означает поломку извлечения, а не
   бесполезность содержимого: после починки парсера его надо разобрать
   заново, и удалять его — значит терять ровно те данные, ради которых
   store и заводился как архив. Удаляются только документы, разобранные
   успешно и давшие ноль фактов.
3. **Сжатие zstd** для объектов больше 64 КБ. JSON-выгрузки жмутся примерно
   в десять раз.
4. Дедупликация даётся content-addressed хранением бесплатно: неизменившийся
   документ при повторном проходе не создаёт нового объекта.

Оценка после сжатия в режиме `facts_only` — порядка 3-5 ГБ на 500 бумаг
за 10 лет. Метаданные в базе (факты вместе с локаторами и сниппетами,
производные величины, котировки) — порядка 1,5-2 ГБ.

**Смена режима не удаляет ничего задним числом.** Переключение с `full`
на `facts_only` меняет поведение только для будущих загрузок. Уже
сохранённые документы удаляются исключительно отдельным явным действием
с подтверждением и списком того, что будет удалено: документ, не давший
фактов сегодня, может понадобиться завтра — при пересмотре peer set,
ручной верификации или починке парсера.

## Решение

1. **Один процесс, один писатель, никакого сервера.** Запись в базу идёт
   из единственного выделенного потока — SQLite сериализует пишущие
   транзакции, и параллельный сбор без этого правила упирается в
   `database is locked`. Чтение — из любого потока в режиме WAL.
   Многопользовательский режим, общий сервер и облачная синхронизация
   в проект не закладываются.
2. **SQLite** — основное хранилище фактов, снапшотов, watchlist, версий
   и истории. Один файл, ноль установки, резервная копия — копия файла.
3. **Content-addressed store на файловой системе** — сырьё, как получено
   от источника, плюс манифесты JSONL.
4. **Всё в одном каталоге данных**, путь настраивается:

```
<app-data>/
  rusterm.db             SQLite
  raw/store/<2>/<sha256> сырые объекты
  raw/manifests/*.jsonl  журнал загрузок
  exports/               выгрузки CSV / Excel
  logs/
  config.toml            настройки
```

5. **Ключ LLM — в системном хранилище секретов** (Keychain на macOS),
   не в `config.toml` и не в репозитории.
6. **Наружу — только за данными:** провайдеры и endpoint LLM. Ни телеметрии,
   ни отправки watchlist или снапшотов на сторону.
7. **Доступ к БД изолирован репозиторным слоем.** Прикладной код не пишет
   SQL напрямую, поэтому смена движка остаётся возможной.

## Если упрёмся

Узкое место — не запись, а аналитические запросы Industry View по всем
компаниям сектора сразу.

**Критерий переключения, а не ощущение:** p95 времени построения
Industry View по сектору из 50 компаний превышает 2 секунды на холодном
кеше, и это не лечится индексами. Тогда рядом добавляется **DuckDB**
для чтения тех же данных, без замены основной БД и без установки сервера.
Метрика измеряется в составе `quality-and-observability.md` и попадает
в журнал операций, чтобы решение принималось по числу. PostgreSQL рассматривается только при отказе
от модели «локальное однопользовательское приложение», то есть при переходе
к общей установке на несколько человек.

## Следствия

1. README §11 и §13 приводятся в соответствие: PostgreSQL заменяется на SQLite.
2. Миграции схемы нужны с Фазы 1: у пользователя на диске лежит база,
   которую нельзя пересоздавать при каждом обновлении приложения.
3. Резервное копирование и перенос описываются в документации как
   «скопировать каталог» — отдельного механизма экспорта базы не требуется.
4. Правовой режим упрощается: данные не покидают компьютер пользователя,
   вопрос перераспространения не возникает, пока приложение не раздаётся
   (см. README §16).

## Отвергнуто

**PostgreSQL.** Требует от пользователя установить и обслуживать СУБД ради
приложения, которое должно запускаться двойным щелчком. Выигрыш по нагрузке
при 500 бумагах и одном пользователе отсутствует. Возвращаемся к вопросу
только при отказе от модели «локальное однопользовательское приложение».
