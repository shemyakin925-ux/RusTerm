# ADR-0001. Модель факта: локатор и lineage

**Статус:** принято (06.09.2026)

## Контекст

README требует, чтобы каждое число в снапшоте разворачивалось до первоисточника
(§3, §9), а разбор рецензии от 05.09.2026 расширил это требование с governance
на все показатели без исключения.

Соблазн на старте — хранить только значение факта, а ссылку на источник считать
задачей UI. Это ошибка, которую нельзя исправить позже: адрес числа внутри
документа ретроспективно не восстанавливается. Чтобы добавить локатор через год,
пришлось бы перепарсить весь накопленный архив сырья заново — а часть источников
к тому моменту сменит вёрстку, формат или состав полей, и часть адресов
не восстановится вообще.

## Решение

**Единица хранения — `Fact`. Факт без локатора не существует: поле обязательное
на уровне схемы, не nullable.**

### Схема Fact

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `fact_id` | uuid | да | первичный ключ |
| `issuer_id` **либо** `listing_id` | str | да | ровно одно: факты отчётности принадлежат эмитенту, котировки — площадке (ADR-0005) |
| `concept` | str | да | код из data dictionary (`revenue`, `ebitda`, …) |
| `period_start` / `period_end` | date | да | для мгновенных величин обе равны |
| `period_type` | enum | да | `instant` / `duration` |
| `value` | decimal | да | как в источнике, без пересчёта |
| `unit` | str | да | `USD`, `shares`, `ratio`, `bbl/day` |
| `currency` | str | нет | если применимо |
| `basis` | enum | да | `as_reported` / `restated` |
| `source_ref` | sha256 | да | объект в raw-store, из которого извлечено |
| `locator` | json | да | адрес числа внутри объекта, см. ниже |
| `origin` | enum | да | `extracted` / `manual` (ADR-0006) |
| `status` | enum | да | `ok` / `suspect` |
| `parser_version` | str | да | версия извлекателя |
| `ingested_at` | ts | да | когда попало в базу |
| `superseded_by` | uuid | нет | заполняется при ревизии, факты не удаляются |

### Типы локатора

```
kind=xbrl     {doc_sha256, fact_id, concept, context_ref, unit_ref, decimals, taxonomy}
kind=table    {doc_sha256, table_index, row, col, header_path[], text_snippet}
kind=pdf      {doc_sha256, page, text_snippet, extractor, extractor_version,
               hint_bbox[x0,y0,x1,y1]}
kind=html     {doc_sha256, css_selector | xpath, char_range[start,end], text_snippet}
kind=api      {endpoint, request_hash, response_sha256, json_pointer}
kind=derived  {inputs[fact_id…], formula_id, method_version}
```

`text_snippet` — не более 200 символов исходного текста вокруг числа. Нужен
для показа пользователю в подсказке и как регрессионный якорь: если источник
переверстал страницу, сниппет перестанет совпадать раньше, чем пользователь
увидит подставленное не то число.

### Производные величины

Вычисленное число — тоже факт, с `kind=derived`. Его локатор перечисляет
факты-входы и `formula_id` с `method_version`. Клик по ROIC разворачивается
в дерево: ROIC → NOPAT и invested capital → статьи отчётности → XBRL-факты
в конкретном 10-K. Дерево строится рекурсивно, глубина не ограничена.

### Что видит верхний слой

`core` отдаёт наружу не голое число, а `Measure{value, unit, method_version,
lineage[]}`, где `lineage` — плоский список локаторов первичных фактов. UI
и LLM работают только с `Measure`.

## Как определяется `basis`

Правило одно и механическое, потому что на глаз это неразличимо:

- **`as_reported`** — факт извлечён из документа, **отчётный период
  которого совпадает с периодом факта**. Годовая выручка 2024 из
  отчёта за 2024 год.
- **`restated`** — факт извлечён из документа за более поздний период,
  где то же число приведено как сравнительное. Выручка 2024 из отчёта
  за 2025 год.

Следствие, ради которого правило и нужно: сравнительные колонки в поздних
отчётах никогда не затирают исходные числа и не создают ложных изменений
в блоке «что изменилось». Расхождение между `as_reported` и `restated`
за один период — это и есть обнаруженная ревизия, отдельное событие,
а не правка.

Документ, вышедший позже, но относящийся к тому же периоду (исправленная
версия отчёта), даёт `as_reported` со своим `source_ref`, а предыдущему
факту проставляется `superseded_by`.

## Правила

1. `locator NOT NULL` на уровне схемы плюс тест, падающий на попытке записать
   факт без локатора.
2. **Тест разрешимости:** `resolve(locator) == value` прогоняется по golden-file
   на сырье из store. Локатор, который не разрешается обратно в то же число, —
   баг сборки, а не косметика.
3. Ревизия отчётности не переписывает факт. Пишется новый факт с
   `basis=restated`, старый получает `superseded_by`. Diff «что изменилось»
   строится по `as_reported`; появление ревизии — отдельное событие.
4. Любая формула имеет `formula_id` и `method_version`. Изменение весов или
   алгоритма — новая версия, пересчёт не затирает историю.
5. Ответ LLM с числом без `lineage` — баг. Проверяется тестом, а не ревью.

## Следствия

1. Схема БД и raw-store фиксируются до первого провайдера — это работа Фазы 1,
   а не оптимизация «потом».
2. Каждый извлекатель обязан возвращать локатор. Провайдер, который умеет
   отдать значение, но не умеет сказать, откуда оно, к интеграции не
   принимается.
3. Объём хранения растёт: локатор и сниппет — порядка 200-400 байт на факт.
   При 500 бумагах и ~2,4 млн фактов вместе с производными это примерно
   0,5-1 ГБ. Приемлемо; политика хранения сырья — в ADR-0003.
4. PDF-источники дороже XBRL примерно вдвое по трудозатратам извлечения,
   потому что bbox нужно получать вместе со значением, а не после.

## Идентичность локатора и подсказки

Координаты `bbox` зависят от библиотеки-экстрактора и меняются при её
обновлении. Поэтому они **не входят в идентичность локатора**: поле
называется `hint_bbox` и служит только подсветке в интерфейсе.

Идентичность локатора PDF задают `doc_sha256`, `page` и `text_snippet`.
`resolve(locator)` обязан работать без `hint_bbox`; смена экстрактора
меняет `extractor_version`, но не `method_version` и не требует пересчёта
фактов. Если же изменится способ определения самого числа — это уже другая
версия парсера.

## Версия схемы локатора

Каждый локатор несёт `schema` (например `pdf.v1`). Формат локатора нельзя
поменять задним числом на накопленном архиве, поэтому изменение схемы —
это новая версия рядом со старой: старые факты сохраняют `pdf.v1`, новые
пишутся с `pdf.v2`, `resolve` умеет обе. Массовая перезапись локаторов
не выполняется никогда.
