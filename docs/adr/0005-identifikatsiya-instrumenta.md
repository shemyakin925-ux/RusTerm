# ADR-0005. Идентификация инструмента

**Статус:** принято (06.09.2026)

## Контекст

Спецификация watchlist адресовала компании тикером: ключ в списке, элементы
групп, имена каталогов снапшотов. Тикер для этого не годится.

- Тикер меняется при ребрендинге, редомициляции, обратном сплите и выходе
  из процедуры банкротства.
- Тикер уникален только в пределах биржи: `BHP` на NYSE и на ASX — разные
  инструменты; `TRMD` торгуется и в Копенгагене, и в Нью-Йорке.
- Тикер переиспользуется: освободившийся символ через год отдают другой
  компании. Список, адресованный тикерами, тогда молча начинает следить
  не за той компанией — это хуже, чем потерять запись.
- У одного эмитента несколько классов акций (`GOOG` / `GOOGL`), отчётность
  одна на всех.

## Решение

**Внутренний `instrument_id` — единственный ключ связи во всей системе.
Тикер — отображаемый атрибут с историей, по нему ищут, но на него не
ссылаются.**

### Три уровня

| Уровень | Что | Ключ |
|---|---|---|
| `issuer` | юридическое лицо, эмитент отчётности | `issuer_id`, привязан к CIK / company number / регистрационному номеру |
| `instrument` | ценная бумага конкретного класса | `instrument_id`, привязан к ISIN |
| `listing` | торговая площадка для инструмента | `listing_id` = биржа + тикер + валюта |

Факты отчётности принадлежат `issuer`. Котировки, объёмы и капитализация
принадлежат `listing`. Мультипликаторы считаются на паре issuer + основной
listing и обязаны фиксировать, какой listing взят.

### Таблица истории тикеров

```
ticker_history{ listing_id, ticker, valid_from, valid_to, reason,
                source_ref }
```

`reason` — из корпоративных действий: `rename`, `redomicile`, `merger`,
`reverse_split`, `exchange_change`. Смена тикера приходит из блока
корпоративных действий (README §3.5) и записывается как событие, а не
как правка справочника.

### Правила

1. Watchlist, группы, peer set, снапшоты, задания планировщика ссылаются
   только на `instrument_id`. Тикеровой строки в этих связях нет нигде.
2. `resolve_ticker(ticker, market)` возвращает `instrument_id` и **дату,
   на которую разрешение верно**. Разрешение тикера без даты некорректно:
   один и тот же символ на разные даты указывает на разные инструменты.
3. Импорт CSV с тикерами (README §5.5) проходит через разрешение; строка,
   которая разрешилась неоднозначно или не разрешилась, попадает в отчёт
   импорта и не добавляется молча.
4. Смена тикера у бумаги из watchlist показывается пользователю как
   событие в «что изменилось», а не применяется бесшумно.
5. При слиянии двух инструментов старый не удаляется: получает
   `superseded_by` и остаётся вместе со своей историей.

## Следствия

1. Справочник инструментов — часть Фазы 1, до первого провайдера.
   Заполняется провайдером и пополняется по мере разрешения тикеров.
2. Каталоги на файловой системе не адресуются тикером. В content-addressed
   store адресация и так по sha256; в SQLite — по `instrument_id`.
3. Экспорт наружу остаётся тикерным — это формат обмена с человеком
   и внешними системами, там `instrument_id` бесполезен.

## ISIN не является обязательным для US

SEC адресует эмитента по CIK и не публикует ISIN. Отсюда важное уточнение
границ, чтобы отсутствие ISIN не выглядело блокером первого рынка:

1. **Ключ связи — `instrument_id`, а не ISIN.** Для US он строится
   на паре CIK эмитента и класса бумаги; сбор отчётности, построение
   снапшота, watchlist и peer set работают без ISIN полностью.
2. **ISIN — необязательный атрибут инструмента.** Заполняется, когда его
   отдаёт провайдер цен либо справочник. Пустое значение — нормальное
   состояние, а не пробел в покрытии.
3. **Без ISIN недоступны ровно две вещи:** импорт списка по ISIN
   и сопоставление одной бумаги, торгующейся на разных рынках. Обе
   деградируют функцию, а не систему, и обе не входят в первую веху.
4. Источник ISIN выбирается вместе с вендором цен и фиксируется тем же
   ADR. До этого поле остаётся пустым, и приложение это допускает.
