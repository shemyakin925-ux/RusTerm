# Процессы и автоматизация

Этап 3 проектирования. Опирается на ADR-0001…0005 и data dictionary.

Автоматизация нужна: карта ручных процессов здесь бессмысленна, потому что
весь смысл продукта — заменить ручной сбор. Проектируются пять процессов.

**Правило узла:** один узел — одна атомарная задача. Узел, который и ходит
в сеть, и парсит, и пишет в базу, не тестируется и не перезапускается.

---

## Общее: свежесть и приоритет

Что считается устаревшим — единственный вход планировщика:

| Блок | Порог свежести | Чем инициируется обновление |
|---|---|---|
| `prices` | 1 торговый день | расписание, после закрытия рынка |
| `fundamentals` | по событию | появление раскрытия в индексе источника |
| `corporate_actions` | 1 день | индекс источника |
| `ownership` | 7 дней | расписание |
| `governance` | 365 дней или публикация proxy | индекс источника |
| `industry_metrics` | вместе с `fundamentals` | каскадом |
| `peer_set` | не устаревает | действие пользователя |
| `llm_summary` | при изменении снапшота | каскадом |

### Бюджет запросов при 500 бумагах

Расчёт по документированному лимиту SEC EDGAR (10 запросов в секунду),
работаем на 5 (`RequestGate`). Оценки ниже — расчётные; строка
`companyfacts` — **замеренная 08.09.2026** на двадцати эмитентах.

| Режим | Запросов | Оценка времени |
|---|---|---|
| Ежедневное обновление | индекс источника 1-2 + цены ~500 + новые раскрытия ~100 | минуты |
| Квартальный пик раскрытий | +500 документов за две недели | минуты в день |
| Первичный сбор 500 бумаг | ~3 000 запросов, из них 500 крупных XBRL | лимитирует не сеть, а объём: ~7,5 ГБ до сжатия, порядка часа |
| **Первичный сбор через `companyfacts`, замер** | **1 запрос на эмитента** (20 эмитентов — 20 запросов) | ~500 запросов на 500 бумаг |

**Поправка от 08.09.2026, по замеру.** Строка «первичный сбор» выше
считает путь через индекс раскрытий: индекс, список документов, тела
отчётов — около шести запросов на эмитента. Путь через
`data.sec.gov/api/xbrl/companyfacts/CIK…json` отдаёт всю историю фактов
эмитента **одним** запросом, то есть в шесть раз дешевле расчёта.
Расхождение больше двойного, поэтому оценка исправлена здесь, а не
списана на погрешность. Исполнитель вынес его в Disputed по ТЗ-8 U8 —
принято. Путь через индекс раскрытий остаётся нужным для документов,
которых нет в XBRL (раскрытия по управлению, инсайдерские сделки).

Это **исправление оценки из Этапа 1**: там я написал «полное обновление —
часы». Верно для полного обхода, но полный обход и не должен происходить
после первичного сбора. При инкрементальном режиме ежедневная работа —
минуты. Часы остаются только у первичного сбора, один раз.

## Процесс 1. Сбор (ingestion)

### Триггеры

Расписание watchlist, ручное «обновить», добавление инструмента, появление
записи в индексе изменений источника.

### Схема

```
[Триггер]
  → 1. plan_refresh — что устарело
        нет заданий → выход
  → 2. poll_source_index — один запрос на источник, не на компанию
        источник недоступен → ветка E1
  → 3. enqueue — план + изменения в очередь, дедупликация по (instrument, блок, дата)
  → 4. fetch — скачать один объект
        429 / 503 → ветка E2
        сеть → ветка E3
  → 5. store_raw — sha256, zstd, запись манифеста
        объект уже есть → пропустить парсинг, задание закрыто
  → 6. parse — извлечь Fact[] с локаторами
        извлекатель не справился → ветка E4
  → 7. validate — единицы, знак, диапазон, resolve(locator), сверка с прошлым периодом
        не прошло → факт помечается suspect, ветка E5
  → 8. persist — транзакция: факты + обновление coverage
  → 9. cascade — пометить зависимые блоки stale (метрики, снапшот, summary)
```

Узел 2 — то, на чём держится инкрементальность: **один запрос к индексу
источника вместо пятисот запросов к компаниям.**

Узлы 1, 3, 6, 7, 8, 9 не ходят в сеть и тестируются офлайн на сохранённом
сырье. Сеть только в 2 и 4.

### Контракт

```json
Job {
  "job_id": "uuid",
  "instrument_id": "str",
  "block": "prices|fundamentals|ownership|corporate_actions|governance",
  "provider": "str",
  "url": "str|null",
  "priority": "int",
  "attempt": "int",
  "created_at": "ts",
  "not_before": "ts|null"
}

FetchResult {
  "job_id": "uuid", "sha256": "str", "bytes": "int",
  "content_type": "str", "fetched_at": "ts",
  "status": "ok|not_modified|error", "error": "str|null"
}

ParseResult {
  "job_id": "uuid", "facts": ["Fact"], "unparsed": "int",
  "parser_version": "str"
}
```

`Fact` — по ADR-0001, поля `locator` и `basis` обязательны.

### Обработка ошибок

| Условие | Действие |
|---|---|
| E1 индекс источника недоступен | 3 повтора с экспоненциальной паузой, затем `coverage=error` по всем блокам источника с причиной; следующий запуск по расписанию пробует снова |
| E2 429 / 503 | уважать `Retry-After`, иначе пауза 2^attempt с джиттером, до 5 попыток; при исчерпании — задание в отложенные, приоритет источника снижается на сутки |
| E3 сетевая ошибка | 3 повтора, затем `coverage=error`, задание в dead-letter с сохранением причины |
| E4 парсер не справился | сырьё сохранено, задание помечается `needs_verification` и попадает в очередь верификатора (процесс 5); блок — `coverage=missing` с причиной, **не** молча пропускается |
| E5 валидация не прошла | факт пишется со статусом `suspect`, участвует в coverage как проблема, в расчёты **не** попадает |
| Дубликат sha256 | задание закрывается успешно без парсинга — это и есть идемпотентность |
| Прерывание процесса | незакрытые задания остаются в очереди; повторный запуск продолжает, а не начинает заново |

## Процесс 2. Сборка снапшота

### Схема

```
[Запрос снапшота | каскад из процесса 1]
  → 1. resolve_instrument — тикер + дата → instrument_id (ADR-0005)
        неоднозначно → вопрос пользователю, не выбор наугад
  → 2. load_facts — факты по basis=as_reported на дату
  → 3. compute_measures — формулы из data dictionary, каждая с method_version
        знаменатель <= 0 → null с причиной, не исключение
  → 4. resolve_peer_set — версия и origin (ADR-0002)
        origin=classifier → пометка unverified
  → 5. compute_percentiles — гейт n >= 5, запись peer_set_version
        n < 5 → перцентили не считаются, показывается таблица
        пир без свежего снапшота → ветка ниже
  → 6. governance_eval — пороги из governance-thresholds.md
        нет данных → серый, никогда не зелёный
  → 7. diff_previous — три раздельных сравнения:
        а) метрики при старом составе peer set
        б) эффект пересостава peer set
        в) появившиеся ревизии (basis=restated)
  → 8. assemble — новая версия снапшота, coverage по блокам
  → 9. render — UI читает готовую версию, ничего не досчитывает
```

### Два прохода, а не один

Узлы 1-3 считаются по одной компании и ни от кого не зависят. Узел 5
зависит от **уже посчитанных** величин пиров: перцентиль компании нельзя
получить, пока у пиров нет своих `measure`. Поэтому сборка по списку идёт
двумя проходами:

1. **Проход по компаниям** — узлы 1-3 и 6 для каждой независимо,
   параллельно.
2. **Проход по секторам** — узлы 4, 5, 7 для тех компаний, чьи пиры
   прошли первый проход.

Правило для пира без свежих данных: он **исключается из расчёта
перцентиля и попадает в состав версии набора с пометкой `excluded_stale`**.
Считать перцентиль по устаревшим значениям пиров нельзя — это то же
молчаливое искажение, ради которого peer set вообще версионируется.
Если после исключения осталось меньше пяти, перцентили не считаются
по общему правилу.

Узел 9 — жёсткая граница: **UI не считает.** Иначе число на экране
перестаёт соответствовать числу в экспорте.

### Контракт

```json
Measure {
  "concept": "str", "value": "number|null", "unit": "str",
  "period": {"start": "date", "end": "date", "type": "instant|duration"},
  "method_version": "str",
  "null_reason": "str|null",
  "lineage": ["Locator"]
}

SnapshotBlock {
  "block": "str", "status": "ready|partial|missing|error",
  "measures": ["Measure"], "reason": "str|null"
}

Snapshot {
  "instrument_id": "str", "snapshot_version": "int", "as_of": "date",
  "peer_set_version": "int|null", "peer_set_status": "verified|unverified|none",
  "blocks": ["SnapshotBlock"]
}
```

## Процесс 3. Массовая операция над watchlist

### Схема

```
[Сообщение пользователя]
  → 1. classify_intent (LLM) — только выбор из списка намерений
        намерение не из списка → уточняющий вопрос
  → 2. extract_params (LLM) — параметры намерения структурой
        обязательный параметр пуст → уточняющий вопрос
  → 3. resolve (детерминированный) — тикеры → instrument_id с датой
        неоднозначно или не найдено → в отчёт, не в добавление
  → 4. apply_filters (детерминированный) — капитализация, отрасль, исключения
  → 5. check_limits — размер результата против лимита операции (100)
        превышен → отдельное подтверждение
  → 6. dry_run — показать список с пометкой по каждой позиции
  → 7. [ЧЕЛОВЕК] подтверждение
        отказ → выход, ничего не изменено
  → 8. apply — одна транзакция: новая версия watchlist целиком
  → 9. audit — запись в audit_log и logs/audit.jsonl
  → 10. enqueue — задания на первичный сбор по новым инструментам
```

Между 1 и 8 состояние не меняется ни разу. Самооценка модели в ветвлении
не участвует (ADR решения Этапа 2): проверки на шагах 3, 4, 5 —
детерминированные.

### Обработка ошибок

| Условие | Действие |
|---|---|
| LLM вернул не-JSON или намерение вне списка | один повтор с жёстким напоминанием формата, затем уточняющий вопрос пользователю |
| Часть тикеров не разрешилась | операция **не** отменяется: разрешённые показываются к добавлению, неразрешённые — отдельным списком с причиной |
| Транзакция на шаге 8 упала | откат целиком, версия не создаётся, пользователю показана причина |
| Пользователь закрыл окно на шаге 7 | ничего не применяется, черновик операции не сохраняется |

## Процесс 4. LLM-summary

```
[Каскад из процесса 2 | запрос пользователя]
  → 1. build_context — снапшот, предыдущий снапшот, раскрытия, peer set
  → 2. generate (LLM) — текст: summary, highlights, risks, citations
  → 3. substitute_and_verify (детерминированный):
        модель возвращает текст с плейсхолдерами {{m:<measure_id>}}
        вместо чисел; приложение подставляет значения из снапшота
        плейсхолдер с неизвестным measure_id → отбраковка
        число цифрами вне плейсхолдера → отбраковка
        не прошло → один повтор; повторно не прошло → ветка ниже
  → 4. persist — llm_summary с model, prompt_hash, snapshot_version
```

Шаг 3 — не проверка стиля, а проверка контракта. Проверять «все ли числа
в тексте есть в снапшоте» разбором готового текста невозможно: год,
количество кварталов и номер пункта — тоже числа, и отличить их от
показателя надёжно нельзя. Поэтому **модель вообще не пишет цифр
показателей**: она ставит плейсхолдер с идентификатором величины,
а подставляет значение приложение. Цифра, написанная моделью напрямую,
означает, что она её сочинила, и текст отбраковывается целиком. При
повторном провале summary не сохраняется, блок остаётся `missing`
с причиной «модель не смогла удержаться в данных». Пустой блок честнее
правдоподобного текста.

## Процесс 5. Верификация факта

Роль, которой не было в спецификации; без неё требование 5 свода
не выполняется.

```
[Пользователь помечает число неверным | E4/E5 из процесса 1]
  → 1. capture — что показано, что должно быть, ссылка на документ
  → 2. store_ground_truth — факт с origin=manual, приоритет над извлечённым
        извлечённый не удаляется, получает superseded_by
  → 3. recompute — пересчёт зависимых Measure
  → 4. propose_golden — предложить пару (сырьё, ожидаемое значение)
        в golden-file набор
  → 5. flag_parser — счётчик расхождений по (провайдер, концепт);
        порог превышен → парсер помечается как деградировавший
```

Шаг 5 — то, что превращает ручные правки в сигнал о поломке источника,
а не в бесконечную ручную работу.
