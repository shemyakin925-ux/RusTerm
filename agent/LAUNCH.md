# Как запустить агента

Актуальное задание — **`agent/TASK-7.md`**, одно на всю ночь. TASK-5
и TASK-6 в него влиты и помечены `SUPERSEDED`: одно ТЗ вместо очереди
из двух — чтобы у автономного агента не было развилки «какой файл брать».

**Область расширена: сеть и модель разрешены.** Раз ZCode — такой же
агент с теми же инструментами, а приложение локальное, то запрет на
реальные источники и на LLM-слой снят. Это первая ночь, когда проект
перестаёт быть проверенным только на синтетике.

Двадцать один пункт T0-T20 строго по приоритету, дальше
`agent/BACKLOG.md`. Порядок оптимизирован под ценность: сначала три
дефекта, которые на реальных данных портили бы факты молча, потом
кратчайший путь к вехе **M2** (пять эмитентов, пять лет, каждое число
разрешается до XBRL-факта), потом **M3**, потом остальное вширь.
Работы заведомо больше, чем на ночь. Финальную приёмку агент прогоняет
сам и кладёт в `agent/ACCEPTANCE-5.txt`.

Задание самодостаточно: способ работы встроен внутрь, `SKILL.md`
и прежние ТЗ читать не нужно.

Для отдачи на независимую проверку — `agent/REVIEW.md`, раздел 4 ниже.

Файл для заказчика, не для агента.

## 0. Итог ночи с 6 на 7 сентября (ТЗ-4): принято

Приёмка на чистой выкладке `agent/night-2` (`a11ec89`): **12 из 13**,
`147 passed, 1 skipped`, ни одного `xfail`. Единственная красная —
проверка 12, и красная она была из-за `origin/main`, а не из-за работы:
скрипт приёмки в ветке содержал проверку 13, которой в `main` ещё не
было. Скрипт опубликован в `main` этим коммитом, стало **13 из 13**.

Оба спорных пункта агента подтвердились — он был прав в обоих.
Найденных дефектов три, вынесены в `TASK-7` пунктами T0-T2: не сделан
инвариант I16 (о нём отчитались, в дереве его нет); лишний
`import sqlite3` внутри `open_connection`; и главный — табличный парсер
не применяет правило basis, а проставляет `as_reported` литералом,
попутно затирая период ячейки. Отчёт агента утверждает обратное. Это
тихо неверные данные, ровно тот класс ошибки, против которого построен
проект, поэтому пункт стоит третьим, а не в бэклоге.

Заодно влит PR #3: код ночи уже написан под ту редакцию
`docs/data-dictionary.md`, и пока PR висел, документация в `main`
противоречила коду в ветке.

**Что требует вашего решения — работа не опубликована.**
`origin/agent/night-2` стоит на `7c010ab`, а локальная ветка — на
`a11ec89`. Семнадцать коммитов ночи (всё ядро И6-И13, этап A, разделы
«Оценка», «Рост», «Котировки») существуют **только на этом ноутбуке**.
Я их не публиковала: пуш кода в публичный репозиторий — необратимое
действие, его решаете вы, а не я.

Пока не запушено, есть два риска: потеря диска уносит всю ночь, и
следующий агент, который клонирует репозиторий с GitHub, получит старое
дерево и начнёт поверх него. Опубликовать так:

```bash
git push origin agent/night-2   # из основной рабочей копии
```

## 1a. Что задать перед запуском: две переменные окружения

Обе читаются из окружения и **не коммитятся** — репозиторий публичный.
Если переменная не задана, соответствующая ветка деградирует на
синтетику, это записывается фактом в отчёт и ночь не блокирует.

**Всё уже прописано в `~/.rusterm.env`** — файл лежит вне репозитория
намеренно, права `600`. Одна команда перед запуском агента:

```bash
source ~/.rusterm.env
```

**1. Контакт для SEC EDGAR — без него в сеть агент не пойдёт.**

SEC требует `User-Agent` с настоящим контактом, иначе блокирует
запросы. В `~/.rusterm.env` ваш адрес уже подставлен:

```bash
export RUSTERM_SEC_UA="Имя Фамилия ваш@адрес.почты"   # в файле — реальный
```

В сам репозиторий адрес не вписан: он уехал бы в логи SEC и в git.
Выдуманный адрес хуже, чем отсутствие сети — ТЗ прямо запрещает агенту
сочинять контакт.

**2. Ключ модели для самого приложения — если хотите, чтобы LLM-слой
проверился на настоящей модели.**

Раскомментируйте две строки в `~/.rusterm.env`:

```bash
export RUSTERM_LLM_PROVIDER=<провайдер>
export RUSTERM_LLM_API_KEY=<ключ>
```

Это ваши деньги: каждый вызов платный. В ТЗ жёсткий потолок — **50
вызовов за ночь**, счётчик в `STATE.json`, дальше отказ. Без ключа
строится и проверяется детерминированная половина (подстановка чисел из
снапшота и валидатор цитат), а настоящий вызов не делается.

Ограничения на сеть, прописанные в ТЗ §1.12, чтобы вас не заблокировали
у первоисточника: только SEC EDGAR, 5 запросов в секунду при
разрешённых десяти, жёсткий потолок 5000 запросов за ночь с отказом,
а не засыпанием; 403 и 429 — остановка и запись, без смены User-Agent,
прокси и зеркал; скачанное никогда не попадает в git и никогда не
попадает в `fixtures/`, где всё помечено синтетикой.

## 2. Что проверить перед запуском

- **Доступ на запись — главное.** Прошлый заход отработал всю ночь и
  не запушил ни одного коммита: работа уцелела только потому, что
  осталась на этом ноутбуке. Выдай токен с правом записи либо впиши
  в сообщение отдельной строкой: «пуш недоступен, утром отдай
  `git bundle create handoff.bundle --all` файлом».
- **Ветка на GitHub должна быть актуальной до старта.** Если вы ещё не
  сделали `git push origin agent/night-2` из раздела 0, агент склонирует
  дерево двухдневной давности и перепишет ночь заново.
- **Собираетесь закрыть репозиторий — сделайте это до запуска и дайте
  агенту токен.** Сейчас GitHub отдаёт `visibility: public`; попытка
  переключения не применилась. Как только репозиторий станет приватным,
  `git clone` в промпте запуска перестанет работать без учётных данных,
  и ночь умрёт на первой же команде. Порядок такой: закрыть
  репозиторий → выдать токен с правами `repo` → проверить клон самому,
  чистой командой, и только потом запускать агента.
- **Всё, что агент запушит, станет публичным немедленно** (пока
  репозиторий открыт). Отозвать
  опубликованное нельзя: форки и зеркала остаются. Поэтому запрет
  выдумывать данные и требование помечать фикстуры синтетическими —
  не гигиена, а защита от того, что придуманное число уедет наружу
  под видом отчётности эмитента. Сейчас правило соблюдено: все пять
  файлов в `fixtures/` помечены `synthetic` и в имени, и внутри.
- В контейнере есть `python3` версии 3.12 или новее и `git`.
- `pytest` ставится из сети. Не встанет — агент по заданию обязан
  продолжить и записать это; проверка 3 тогда не пройдёт, и это
  честный результат, а не провал.

## 3. Что сделать утром

```bash
cd RusTerm
git fetch origin && git checkout agent/night-2
bash agent/acceptance.sh
```

Дальше по порядку:

1. **Код возврата скрипта.** 0 — принято. Иначе он сам печатает,
   что именно не сошлось.
2. **`git diff origin/main -- agent/acceptance.sh`** — обязан быть
   пустым. Непустой означает, что агент правил приёмку; всё остальное
   после этого можно не читать.
3. **`agent/ACCEPTANCE-5.txt`** — прогон приёмки, который агент сделал
   сам. Затем `agent/REPORT-7.md`, разделы «HANDOFF» и «What not to
   trust» — до раздела «Done».
4. **`git log --oneline origin/agent/night-2..agent/night-2`** — если
   непусто, работа не опубликована, см. раздел 0.
5. **Раздел «Disputed»** в отчёте — там места, где агент считает
   задание или скрипт неправыми. В прошлый заход он был прав дважды
   из двух.

Отчёт и скрипт расходятся — верить скрипту.

## 4. Что отправить рецензенту

Для независимой проверки — своё сообщение. Отдавать можно нескольким
моделям сразу, ответы сравнимы за счёт формата из `agent/REVIEW.md` §8.

```text
Проверь чужой проект как независимый рецензент. Код писали автономные
агенты, их отчёты содержат недостоверные утверждения — верь только тому,
что запустишь сам.

    git clone https://github.com/shemyakin925-ux/RusTerm.git
    cd RusTerm && git checkout agent/night-2
    python3 -m pip install pytest
    cat agent/REVIEW.md

agent/REVIEW.md — бриф проверки: что за проект, что реально сделано,
какие дефекты уже найдены, что смотреть и в каком виде отвечать.
Он самодостаточен, начни с него.

Ничего не чини и не коммить. Твоя задача — найти и описать, а не
исправить. Находка без способа воспроизвести — гипотеза, так её
и помечай.
```

Отправляй **одинаковый** текст каждой модели и сравнивай ответы:
находка, которую увидели двое независимо, почти наверняка настоящая;
одиночная — требует проверки.
