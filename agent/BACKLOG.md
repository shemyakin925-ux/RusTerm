# Отложенные дефекты

Найдены, воспроизведены, в текущее задание не входят: каждый требует
проектного решения, а не правки. Берутся после этапа B (`TASK-5.md` T8).

Не удалять и не «закрывать» без записи о том, что именно сделано.

---

## Б1. Миграция не снимает резервную копию базы

`docs/data-model.md` §8 п.4: «Перед миграцией снимается копия
`rusterm.db` рядом; удаляется после успешного применения».
Docstring `rusterm/store/db.py` повторяет это же обещание строкой 7.
В коде нет ни `shutil.copy`, ни `os.replace`, ни временного файла —
проверено `grep`, совпадений ноль.

Пока миграции были только `CREATE TABLE IF NOT EXISTS`, цена ошибки
была нулевой. С появлением миграции 33, пересобирающей таблицу
с переносом данных (`TASK-5.md` T1), сбой посередине уносит
единственную копию.

Решать вместе с T1 или сразу после него.

## Б2. Запись в store не атомарна

`rusterm/store/raw_store.py`, строки 148 и 152: `target.write_bytes(…)`
напрямую, без записи во временный файл и `os.replace`. Падение процесса
или диска оставит обрезанный объект, который `has_object` сочтёт
существующим, а `read_object` вернёт мусор.

Store — единственный архив первоисточников; повреждённый объект ломает
lineage и `resolve(locator)`, то есть саму способность показать, откуда
взялось число.

## Б3. Сбой в `RawRepo.put` оставляет сирот

`rusterm/store/repos.py`, `RawRepo.put`: объект пишется на диск, строка
дописывается в манифест, и только потом идёт `INSERT` в `raw_object`.
Исключение на вставке оставляет файл и манифест без строки в базе.
Воспроизведено на базе со старым `CHECK`:

```
1-й put упал: IntegrityError
  объект на диске : True
  строк в БД      : 0
  строк манифеста : 1
```

Повторный `put` строку в базе **чинит** (0 → 1) — вопреки первому
впечатлению, `ON CONFLICT DO NOTHING` этому не мешает. Но он же
дописывает в манифест второй экземпляр той же записи:

```
после повторного put:
  строк в БД      : 1
  строк манифеста : 2
```

То есть дефекта два: окно несогласованности «файл ↔ манифест ↔ индекс»
и дубли в append-only манифесте, которые исказят восстановление индекса.

## Б4. Движок миграций умеет только создавать таблицы

`_MIGRATIONS` — список `CREATE TABLE IF NOT EXISTS`, версия равна
индексу. Изменить колонку или `CHECK` у существующей таблицы механизм
не может; `TASK-5.md` T0 и T1 добавляют многооператорные миграции, но
это заплатка под конкретный случай, а не механизм эволюции схемы.

Отдельно: `checksum` каждой миграции записывается в `schema_version`,
но **никогда не сверяется** с текущим SQL. Правку уже применённой
миграции — ту самую, что породила дефект Д1, — движок не заметил бы
даже теоретически.

Минимум: сверять checksum применённых версий при старте и падать
с внятной ошибкой при расхождении.

## Б5. Нет фабрики соединения с обязательными PRAGMA

`sqlite3.connect` не вызывается в пакете ни разу — только в тестах,
где `PRAGMA journal_mode=WAL` и `foreign_keys=ON` выставляются руками
в каждом. Первый же вызывающий код (CLI, конвейер), забывший PRAGMA,
получит другое поведение блокировок и **отключённые внешние ключи**.

Дефект латентный ровно до появления такого кода, то есть до этапа B.
Нужна одна функция `open_db(path)`, выставляющая PRAGMA и возвращающая
соединение, и запрет на `sqlite3.connect` мимо неё.
