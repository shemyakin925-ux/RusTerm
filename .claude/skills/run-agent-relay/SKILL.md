# Эстафета координатора и исполнителя

Драйвер — [agent/relay.py](../../../agent/relay.py) (пути ниже — от корня
репозитория). Это не описание процесса из `CLAUDE.md`, а его реализация:
один файл `agent/BATON.json` на ветке смены говорит, чей ход, а команда
`wait` **блокирует** до перехода хода. Поэтому отчёт виден сразу, а не
«когда заглянешь», и исполнитель получает ТЗ в рабочее дерево сам.

Обмен идёт через `origin`: обе стороны пишут ветку смены (`agent/night-N`),
но по очереди — держатель эстафеты пишет, второй ждёт. Гонок нет по
построению.

## Что нужно

- `python3` (здесь 3.14.6, только стандартная библиотека) и `git`;
- право push в `origin` на ветку смены у обеих сторон;
- ветка смены уже существует на `origin`.

Ставить нечего: `pip install` не нужен.

## Завести эстафету (один раз на смену)

```bash
python3 agent/relay.py --branch agent/night-clean init --holder executor --round 42 --task agent/TASK-42.md --report agent/REPORT-42.md --note "shift start"
```

Подставь свою ветку смены (`agent/night-11`) и номер круга — номер ТЗ.
Ветка запоминается в `.git/relay-branch`, дальше `--branch` можно не
писать. Кто держит первым — тот, кому выдано ТЗ (обычно `executor`).

## Цикл координатора (главный путь)

**Шаг 1 — ждать ход. Запускать только в фоне** (`run_in_background: true`):
фоновая команда переживает ход диалога и сама разбудит сессию, когда
исполнитель вернёт эстафету.

```bash
python3 agent/relay.py wait --for coordinator --timeout 3600 --interval 20
```

Коды возврата — это и есть протокол: `0` ход твой, `2` таймаут (перезапусти
ожидание), `3` пауза, `4` цикл закрыт, `5` ошибка.

**Шаг 2 — разобрать отчёт одной командой.** Ровно тот порядок чтения,
который требует `CLAUDE.md`: HANDOFF, Disputed, Blocked, «чему верить
нельзя», затем коммиты, `diff --stat` и стражи (удалённые `assert` в
`tests/`, тронутые `acceptance.sh`/`selfcheck.sh`/`docs/`).

```bash
python3 agent/relay.py --branch agent/night-11 digest --base main --lines 14
```

**Шаг 3 — прогнать приёмку.** Отдельное рабочее дерево на голове ветки
смены; своё дерево координатора не трогается. Путь по умолчанию уникален
на прогон (ТЗ-88 C1), поэтому `--worktree` не указывают: один общий путь
на всю машину передавал мусор одного прогона следующему.

```bash
python3 agent/relay.py --branch agent/night-11 verify
```

Верить этому прогону, а не отчёту. Код возврата печатается последней
строкой.

**Шаг 4 — написать `agent/TASK-{N+1}.md`** (в своём рабочем дереве, на
своей ветке — переключаться на ветку смены не нужно) **и передать ход**.
`hand` соберёт коммит плюмбингом поверх `origin/<ветка>` и запушит его:

```bash
python3 agent/relay.py hand --to executor --task agent/TASK-32.md --report agent/REPORT-32.md --add agent/TASK-32.md --note "Verdict: five. D1 returns the assert you dropped."
```

`--add` повторяется для каждого файла, который уезжает вместе с эстафетой
(`agent/BACKLOG.md`, `agent/CONTEXT.md`, `agent/LAUNCH.md`).

**Шаг 5 — снова шаг 1.** Круг замкнулся. **Не заканчивай ход, не запустив
следующий `wait` в фоне**: пока фоновая команда жива, отчёт исполнителя сам
разбудит сессию; как только её нет — цикл встал и ждёт человека.

## Что должно быть в каждом ТЗ, чтобы круг замкнулся с той стороны

Исполнитель участвует в эстафете двумя командами. Блок вставляется в
`agent/TASK-NN.md` (см. `agent/PROTOCOL.md` §12):

```
- **Relay:** сдать работу — `python3 agent/relay.py hand --to coordinator
  --report agent/REPORT-NN.md --note "<одна строка>"`; затем
  `python3 agent/relay.py wait --for executor --timeout 3600` — она
  подтянет ветку и назовёт следующий файл ТЗ.
```

`wait --for executor` при выкаченной ветке смены делает
`git pull --rebase --autostash`, поэтому новое ТЗ оказывается на диске
само — «сразу видит задание» здесь буквально.

## Пауза, продолжение, конец — путь пользователя

```bash
python3 agent/relay.py status
python3 agent/relay.py pause --note "перекур"
python3 agent/relay.py resume
python3 agent/relay.py finish --note "смена окончена"
```

- `pause` кладёт стоп-файл в `.git/relay-stop`: здешний `wait` сразу
  выходит с кодом `3`, а `hand` отказывается передавать ход. Если
  эстафету в этот момент держит эта сторона, пауза ещё и пушится в
  `BATON.json` — тогда её видит второй агент. Если держит вторая сторона,
  она узнает о паузе, когда вернёт ход.
- `resume` снимает и локальную паузу, и флаги `paused`/`finished` на ветке.
- `finish` закрывает цикл: любой `wait` выходит с кодом `4`.

## Подводные камни

- **Координатору нельзя выкатывать ветку смены.** `hand` и `init`
  собирают коммит через `read-tree`/`commit-tree` и пушат его напрямую,
  ничего не меняя в рабочем дереве. Если выкатишь — начнутся ребейзы
  и конфликты с исполнителем.
- **Пока ход не твой, не пуши в ветку смены руками.** Первый же
  прогон это показал: исполнитель сделал `git push` после того, как
  координатор положил эстафету, и получил `! [rejected] (fetch first)`.
  Лечится тем, что `hand`/`wait` сами делают `pull --rebase --autostash`.
- **Провалившийся `hand` раньше оставлял локальный коммит эстафеты**, и
  следующая попытка ловила `CONFLICT (add/add): agent/BATON.json`. Теперь
  при отказе push коммит снимается (`reset --mixed`), файлы остаются в
  дереве. Если всё же увидел дерево в середине ребейза — `git rebase
  --abort`, затем `python3 agent/relay.py status` и повторить.
- **Не дописывай `; echo "EXIT=$?"` к фоновому `wait`.** Тогда
  уведомление о фоновой команде покажет код `echo`, то есть `0`, и
  таймаут (`2`) будет неотличим от «пришёл отчёт». Запускай `wait`
  единственной командой и читай его последнюю строку.
- **Таймаут — норма, а не сбой.** Первый боевой круг на `agent/night-11`
  истёк по часу, пока исполнитель работал над C3 (`STATE.json`:
  `status=working`, и его коммит уже лежал на ветке). Ответ на код `2` —
  снова запустить `wait` в фоне, а не будить человека.
- **`hand` берёт только своё.** Раньше он делал обычный `git commit`, и
  всё, что уже лежало в индексе исполнителя, уезжало под заголовком
  «Эстафета: круг N» — так работа по ТЗ-37 I5 попала в коммит `fa6fb08`.
  Теперь коммит собирается `--only` по своим путям, а чужое в индексе
  печатается предупреждением.
- **Кешированная ветка одна на клон.** `--branch` пишет
  `.git/relay-branch`, поэтому один прогон с чужой веткой (например по
  тестовому стенду) молча перенаправит следующие команды туда же. Лечится
  явным `--branch agent/night-N`; проверять — `relay.py status`, первая
  строка называет ветку.
- **`verify` гоняет приёмку в подключённом рабочем дереве** (`git worktree
  add`), а там `.git` — файл, не папка. Это ловит настоящие допущения кода
  (ТЗ-37 I5 краснел именно так), но помни: окружение приёмки отличается от
  клона исполнителя. Прежде чем возвращать работу — воспроизведи и назови
  причину, как это сделано в вердикте по ТЗ-37.
- **`wait` в переднем плане блокирует сессию** на весь таймаут. Всегда
  `run_in_background: true`; уведомление о завершении фоновой команды —
  и есть сигнал «пришёл отчёт».
- **`digest --base main` покажет пусто**, если ветку смены уже влили в
  `main` (на влитые ветки смены это и есть). Для уже влитой смены сравнивай
  с базой до влития: `--base <sha>`.
- **Номер отчёта берётся ведущим числом**: `REPORT-20-000.md` — это 20,
  а не 20000, иначе автовыбор «самого свежего» промахивался мимо
  `REPORT-30.md`.
- **`.claude/` у пользователя в глобальном `.gitignore`**, поэтому сам
  драйвер лежит в `agent/relay.py` (обычный tracked-файл, доезжает к
  исполнителю через git), а этот `SKILL.md` добавлен в индекс
  принудительно: `git add -f .claude/skills/run-agent-relay/SKILL.md`.
- **`verify` на ветке, отставшей от `origin/main`, даёт ложный провал
  пункта 10.** Приёмка сравнивает `git diff origin/main HEAD -- docs/`,
  поэтому ADR, добавленный в `main` уже после смены, выглядит на старой
  ветке удалённым. Реальный прогон на прежней (уже влитой) ветке смены дал
  «пройдено 12, провалено 1» ровно по этой причине
  (`D docs/adr/0019-net-vendorskogo-adjusted.md` — файл есть на
  `origin/main` и нет на ветке смены). Провал пункта 10 всегда сверяй с
  `git log origin/main -- <файл>`, прежде чем возвращать работу.
- **Код возврата приёмки печатается отдельной строкой** — потому что
  через `| tail` виден код `tail`, а не приёмки. Читай строку
  «код возврата приёмки: N», а не `$?` конвейера.
- **Полный прогон `verify` идёт минутами** (набор гоняется дважды — с
  `zstandard` и без): запускай его тоже в фоне, а не в переднем плане.
- **Стоп-файл живёт в `.git/relay-stop`** — он не виден ни в
  `git status`, ни в коммите (P3/P4 из `agent/PROTOCOL.md` не нарушены).
- Эстафета не отменяет `agent/STATE.json`: исполнитель ведёт его как
  прежде, `digest` и `status` его показывают.

## Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| `relay: ветка смены неизвестна` | один раз передать `--branch agent/night-N`, дальше помнится |
| `! [rejected] ... (fetch first)` при своём push | `git pull --rebase --autostash origin <ветка>`, затем повторить; ход отдавать только через `hand` |
| `relay: push отклонён: origin/<ветка> ушла вперёд` | `python3 agent/relay.py status`, перечитать чужой коммит, повторить `hand` |
| `CONFLICT (add/add): agent/BATON.json` | `git rebase --abort`; снять свой локальный коммит эстафеты (`git reset --hard origin/<ветка>` — только если своей несданной работы в нём нет) |
| `эстафета на origin/<ветка> не заведена` в `digest` | `relay.py init` — либо разбирать отчёт руками: `digest --report agent/REPORT-NN.md` работает и без эстафеты |
| `wait` вышел с `2` | это не ошибка, а таймаут: запустить `wait` снова (в фоне) |
| `wait` вышел с `3`, а паузу никто не ставил | проверить `.git/relay-stop` — `relay.py resume` его убирает |
| `verify` красит пункт 10 на `docs/` строкой `D <файл>` | ветка отстала от `origin/main`: файл добавлен в main после смены. Проверить `git log origin/main -- <файл>`; это не нарушение исполнителя |

## Чем это проверено

Полный круг прогнан на тестовом стенде из трёх репозиториев (голый
«origin» плюс клоны координатора и исполнителя): `init` → исполнитель
сдал отчёт и удалил `assert` → фоновый `wait --for coordinator` сам
проснулся → `digest` показал удалённый `assert` → `verify` дал код 0 →
координатор выдал `TASK-32.md` → фоновый `wait --for executor` подтянул
его в рабочее дерево. Отдельно прогнаны `pause`, `resume`, `finish`,
таймаут и отказ `hand` при паузе. `digest` и `verify` прогнаны на
настоящей (не тестовой) ветке смены: разделы реального
`REPORT-30.md` разобрались верно, приёмка отработала целиком и дала
«пройдено 12, провалено 1» — единственный провал разобран выше как
артефакт отставшей ветки. Ни одного push в боевой репозиторий из этой
сессии не сделано.
